# ADR-002: 2D 桌宠资源管线

> **⚠️ 状态变更 2026-05-01(post-M0)**:本 ADR 选定的 **Live2D Cubism 4** 路线已**废止**。项目改为 **3D VRM**(Three.js + `@pixiv/three-vrm`)。
>
> 触发原因:
> 1. Live2D Cubism Core 4 → 5 → 6 存在破坏性 ABI 升级(`getDrawableRenderOrders` 改名等),`pixi-live2d-display` 上游 2022 年起停更,社区 fork(lipsyncpatch / mulmotion)未跟进 Core 6
> 2. Live2D Editor Pro 商用授权年费 + 专业 Live2D 美术招聘门槛高,与"开源项目"的当前定位不符
> 3. VRM 是 Pixiv / VRM Consortium 推的开放标准,`@pixiv/three-vrm` 官方维护,VRoid Studio 免费创作,VRoid Hub 万级免费模型生态
>
> 受影响 ADR:ADR-003(配饰 native 插槽 → VRM humanoid bone attach / VRMC_node_constraint)、ADR-004(Live2D motion ID → VRM animation clip 名)。
>
> 下方原决策内容保留作为历史背景,**实施期不再参考**。

## 背景

PRD v0.6 锁定"2D 桌宠",但具体资源管线未定。这是本项目美术工作量与表现力的核心决策,直接影响:
- 美术工作量(分图层建模 vs 骨骼动画 vs 序列帧绘制)
- 桌宠表现力(动作丰富度 / 流畅度)
- 安装包大小
- 运行时内存与 GPU 占用
- 装扮(O)与物理交互(N)的可叠加性

## 备选方案

### 选项 A: Live2D Cubism 4

**特征**
- 分图层 PSD/PNG 建模 + 参数化变形
- 通过 Live2D Cubism Web SDK 在 Tauri WebView 中运行
- 支持插槽叠加(可作为配饰挂载点)

**优点**
- 桌宠社区主流方案,资源丰富(可购买 / 委托 / 自建)
- 表现力强,微表情 / 呼吸感 / 头部追踪都可
- **支持运行时 layered sticker 叠加**(对模块 O 装扮关键)
- 文件体积合理(单模型 ~2-5MB)

**缺点**
- **商业授权成本**:Cubism Editor Pro 年费 + 商用许可(具体看授权类型)
- 美术建模需要专业 Live2D 美术(不是普通 2D 绘师)
- WebGL 上下文初始化在低端机上略卡

### 选项 B: Spine 2D

**特征**
- 骨骼动画 + skin 切换
- esoteric software 提供 SDK

**优点**
- 动画质量高,适合复杂运动(逛桌面、抗议等)
- skin 切换原生支持(整套换装方便)

**缺点**
- **不擅长 layered sticker 任意叠加**(skin 是整体替换,配饰叠加需要 hack)
- Spine 商用授权按团队规模分级,小团队还可,扩张后费用陡增
- 美术管线需要 Spine Editor + 专业骨骼建模能力
- WebGL 集成示例少于 Live2D

### 选项 C: PNG 序列帧 / SVG 关键帧

**特征**
- 每个动作一组 PNG 帧 / SVG 路径
- Canvas / WebGL 直接绘制

**优点**
- **零授权成本**
- 美术门槛最低(任何 2D 绘师都能做)
- 调试简单

**缺点**
- **表现力极弱**:每个动作一组帧,组合爆炸
- **文件体积大**:多动作 + 多装扮叠加时 PNG 帧数膨胀
- **配饰叠加需自研**:没有现成 SDK
- 微表情 / 呼吸感等连贯效果几乎不可能

## 关键评估维度对比

| 维度 | Live2D | Spine | PNG 序列帧 |
|---|---|---|---|
| 表现力 | ★★★★★ | ★★★★ | ★★ |
| 配饰叠加(模块 O) | ★★★★★ native | ★★ hack | ★ 自研 |
| 物理交互动作丰富度(N) | ★★★★ | ★★★★★ | ★★ |
| 美术成本 | 中-高 | 中-高 | 低 |
| 商业授权 | 年费 | 按规模 | 无 |
| 包体积 | 2-5MB/模型 | 1-3MB/模型 | 5-30MB(多动作) |
| WebGL 性能 | 中 | 中 | 低-中 |
| Tauri WebView 集成示例 | 多 | 少 | 自研 |

## 我的倾向

**🌟 倾向选项 A(Live2D Cubism 4)**,关键理由:
1. **配饰叠加 native 支持**——对模块 O 装扮决定性。
2. 桌宠表现力是产品差异化的视觉基础。
3. 社区资源丰富,可降低初始美术成本。

**前置 spike**:
- M0 第 2-3 日做 1 天 spike,验证 Live2D Cubism Web SDK 在 Tauri WebView 中的:
  - 启动期初始化耗时(目标 < 800ms)
  - 内存占用(目标 < 60MB / 单模型)
  - 运行时挂载 PNG sticker 配饰的可行性

若 spike 失败 → 降级路线:
- **不降级到 PNG 序列帧**(损失太大)
- **可降级到 Live2D + "整套皮肤"** 模式(放弃配饰叠加,O 模块仅做整体皮肤切换;牺牲使用率指标 11.17,但保留 11.15-11.16/18-20)

## 决策

**选定:Live2D Cubism 4 + Web SDK**(选项 A)。

关键理由:Live2D 是唯一对模块 O 装扮的"运行时 layered sticker 任意叠加"提供 native 支持的方案(通过 Cubism Editor 的 parameter group 预留挂载点);桌宠表现力是产品差异化的视觉基础(微表情/呼吸/头部追踪);社区资源丰富,可降低初始美术成本。

**前置 spike**:M0 末做 1 天集成验证,目标:启动期初始化 < 800ms / 单模型内存 < 60MB / 运行时挂载 PNG sticker 配饰可行。

**降级路线**(spike 失败时):降级到 Live2D + "整套皮肤"模式(放弃配饰自由叠加,模块 O 仅做整体皮肤切换)。**不**降级到 PNG 序列帧或 Spine。

## 后果

### 正面
- 配饰叠加 native 支持,模块 O 的"自由搭配"体验可实现(KPI 11.17)。
- 桌宠表现力强,微表情/呼吸/头部追踪都可达成。
- 资源体积合理(单模型 ~2-5MB),与 PRD §10.5 总安装包 ≤ 80MB 一致。

### 负面
- Cubism Editor Pro 年费 + 商用许可成本(具体看授权类型,需法务/财务确认)。
- 美术建模需要专业 Live2D 美术(不是普通 2D 绘师),招聘/外包门槛高。
- WebGL 上下文初始化在低端机上略卡,需要监控 spike 数据决定是否做 lazy init。
